# **PART 1 — JAVA COLLECTIONS FRAMEWORK**

## **1. Java Collections Framework Deep Dive**

### **1.1 What is the Java Collections Framework?**

The Java Collections Framework (JCF) is a collection of interfaces, classes, and algorithms used to store and manipulate groups of objects.

Without collections, you might store data using arrays:

```
String[] students = new String[5];

students[0] = "Amit";
students[1] = "Rahul";
students[2] = "Priya";
students[3] = "Neha";
students[4] = "Arjun";
```

Arrays work well when you know the required size in advance. But they have limitations:

- Their size is fixed after creation.
- Inserting and deleting elements can require manual shifting.
- They do not automatically provide operations such as sorting, searching, or removing duplicates.
- Implementing complex data structures manually takes additional effort.

Collections provide reusable data structures and operations.

```
import java.util.*;

public class Main {
    public static void main(String[] args) {

        List<String> students = new ArrayList<>();

        students.add("Amit");
        students.add("Rahul");
        students.add("Priya");

        students.remove("Rahul");

        System.out.println(students);
    }
}
```

Output:

```
[Amit, Priya]
```

The framework handles much of the underlying data management.

### **1.2 The Collections Framework hierarchy**

The most important interfaces are:

## **Collections Framework**

**Iterable**

Provides iteration support

**Collection**

General group of elements

**List**

ArrayList

Vector

PriorityQueue

Stores key-value pairs

HashMap

A common interview question is:

**Why is Map not a child of Collection?**

Because a `Collection` represents a group of individual elements, whereas a `Map` represents relationships between keys and values.

For example:

```
List<String> names = new ArrayList<>();

names.add("Amit");
names.add("Rahul");
```

Here, each element is a name.

But:

```
Map<Integer, String> students = new HashMap<>();

students.put(101, "Amit");
students.put(102, "Rahul");
```

Here, every entry contains a key and a value.

### **1.3 Important collection interfaces**

| Interface | Purpose                              | Example                |
| --------- | ------------------------------------ | ---------------------- |
| List      | Ordered elements, duplicates allowed | Student names          |
| Set       | Unique elements                      | Unique email addresses |
| Queue     | Elements waiting to be processed     | Task queue             |
| Deque     | Insert and remove at both ends       | Sliding window         |
| Map       | Key-value relationships              | Student ID → Name      |

### **1.4 Collection algorithms**

The `Collections` utility class provides useful algorithms.

```
import java.util.*;

public class Main {

    public static void main(String[] args) {

        List<Integer> numbers =
            new ArrayList<>(Arrays.asList(50, 20, 40, 10, 30));

        Collections.sort(numbers);

        System.out.println(numbers);

        Collections.reverse(numbers);

        System.out.println(numbers);

        Collections.shuffle(numbers);

        System.out.println(numbers);

        System.out.println(Collections.max(numbers));

        System.out.println(Collections.min(numbers));
    }
}
```

Common operations include:

- `Collections.sort()` — sorts a list.
- `Collections.reverse()` — reverses the order.
- `Collections.shuffle()` — randomly shuffles elements.
- `Collections.max()` — finds the maximum.
- `Collections.min()` — finds the minimum.
- `Collections.frequency()` — counts occurrences.
- `Collections.binarySearch()` — searches a sorted list.

### **1.5 Iterators and fail-fast behaviour**

An iterator allows you to traverse a collection.

```
List<Integer> numbers =
    new ArrayList<>(Arrays.asList(10, 20, 30, 40));

Iterator<Integer> iterator = numbers.iterator();

while (iterator.hasNext()) {

    int value = iterator.next();

    System.out.println(value);
}
```

You can remove elements safely through the iterator:

```
Iterator<Integer> iterator = numbers.iterator();

while (iterator.hasNext()) {

    int value = iterator.next();

    if (value == 20) {
        iterator.remove();
    }
}
```

What happens when you modify an `ArrayList` directly while iterating over it?

```
for (Integer number : numbers) {
    numbers.remove(number);
}
```

This commonly produces a `ConcurrentModificationException`.

This happens because many standard collection iterators are **fail-fast**. They detect structural modifications made outside the iterator and may throw an exception.

Fail-fast behaviour is a bug-detection mechanism, not a thread-safety guarantee. It is best-effort, so you must not depend on it for synchronization.

**When to use collections:**

Use `List` when sequence and positional access matter, `Set` when uniqueness matters, `Queue` when processing order matters, and `Map` when you need to look up values by keys.

## **2. ArrayList Internals**

### **2.1 What is ArrayList?**

`ArrayList` is a resizable array implementation of the `List` interface.

Unlike a normal array, its capacity can grow when more elements are added.

```
List<Integer> numbers = new ArrayList<>();

numbers.add(10);
numbers.add(20);
numbers.add(30);

System.out.println(numbers.get(1));
```

Output:

```
20
```

### **2.2 How does ArrayList work internally?**

An `ArrayList` internally maintains:

1. An array that stores references to elements.
2. A `size` representing the number of actual elements.
3. A capacity representing the length of the internal array.

Consider:

```
ArrayList<Integer> numbers = new ArrayList<>();

numbers.add(10);
numbers.add(20);
numbers.add(30);
```

Conceptually, the internal array might look like this:

**Internal array example**

## **10**

Index 0

## **20**

Index 1

## **30**

Index 2

## **null**

Index 3

## **null**

Index 4

## **null**

Index 5

Size = 3

Capacity = 6

The diagram is illustrative. The actual capacity depends on how the list was created and grown.

The list contains three elements even though the internal array has room for six.

**Size and capacity are different.**

- Size: Number of stored elements.
- Capacity: Number of elements the internal array can hold before it must grow.

### **2.3 How does insertion work?**

Suppose the internal array has available space.

```
numbers.add(40);
```

The new element is inserted at the next free position.

```
Before:

[10, 20, 30, null, null]

After:

[10, 20, 30, 40, null]
```

This normally takes constant amortized time.

What if the array becomes full?

### **2.4 Dynamic resizing**

Suppose the capacity is four and all four positions are occupied.

```
[10, 20, 30, 40]
```

You execute:

```
numbers.add(50);
```

The list needs a larger internal array.

Conceptually:

1. Check whether the current array has enough capacity.
2. Allocate a larger array.
3. Copy the existing elements into it.
4. Add the new element.
5. Use the new array internally.

**Dynamic resizing**

Illustrative example

Before growth

10

20

30

40

After allocating a larger array

10

20

30

40

50

empty

The actual capacity growth strategy is an implementation detail. Common OpenJDK ArrayList implementations grow the capacity by approximately 50% when they need to expand it.

Resizing requires copying existing references, so one insertion can take \(O(n)\) time.

However, resizing does not happen on every insertion.

Over many insertions, the average cost per insertion remains **amortized** \(O(1)\).

### **2.5 Inserting in the middle**

Consider:

```
List<Integer> numbers =
    new ArrayList<>(Arrays.asList(10, 20, 30, 40));

numbers.add(1, 15);
```

The element `15` is inserted at index 1.

The existing elements must shift right.

```
Before:

[10, 20, 30, 40]

After:

[10, 15, 20, 30, 40]
```

This takes \(O(n)\) time in the worst case.

### **2.6 Removing elements**

```
numbers.remove(1);
```

The element at index 1 is removed. Elements after it shift left.

This generally takes \(O(n)\).

### **2.7 ArrayList time complexity**

| Operation           | Time complexity      |
| ------------------- | -------------------- |
| `get(index)`        | \(O(1)\)             |
| `set(index, value)` | \(O(1)\)             |
| `add(value)`        | Amortized \(O(1)\)   |
| `add(index, value)` | \(O(n)\)             |
| `remove(index)`     | \(O(n)\)             |
| `contains(value)`   | \(O(n)\)             |
| Iteration           | \(O(n)\)             |

### **2.8 ArrayList optimization**

When you know approximately how many elements you will store, reserve capacity in advance.

```
ArrayList<Integer> numbers = new ArrayList<>();

numbers.ensureCapacity(100000);
```

This can reduce repeated resizing.

You can also construct the list with an initial capacity:

```
ArrayList<Integer> numbers =
    new ArrayList<>(100000);
```

Notice that this sets capacity; it does not create 100,000 actual elements.

### **2.9 When should you use ArrayList?**

Use `ArrayList` when:

- You frequently access elements by index.
- You mostly add elements at the end.
- You iterate over elements frequently.
- You do not frequently insert or delete elements near the beginning.

It is a strong default choice for general-purpose lists.

## **3. LinkedList Internals**

### **3.1 What is LinkedList?**

A `LinkedList` is a doubly linked list.

Unlike `ArrayList`, it does not store all elements in one continuous array.

Instead, every element is stored inside a separate node.

Each node contains:

- The stored element.
- A reference to the previous node.
- A reference to the next node.

### **3.2 Internal node structure**

Conceptually, a node looks like this:

```
class Node<E> {

    E item;

    Node<E> previous;

    Node<E> next;
}
```

This is an educational representation of the underlying structure.

### **3.3 How does a LinkedList work?**

Consider:

```
LinkedList<Integer> numbers =
    new LinkedList<>();

numbers.add(10);
numbers.add(20);
numbers.add(30);
```

Its nodes are connected:

**Doubly linked list**

# **10**

Node 1

# **20**

Node 2

# **30**

Node 3

Previous references

Next references

Each node links to both its previous and next node. The list also maintains references to its first and last nodes.

### **3.4 Insertion at the beginning**

```
numbers.addFirst(5);
```

Conceptually:

```
Before:

10 ⇄ 20 ⇄ 30

After:

5 ⇄ 10 ⇄ 20 ⇄ 30
```

Only a few references need to change.

Therefore, adding at the beginning takes \(O(1)\).

### **3.5 Insertion at the end**

```
numbers.addLast(40);
```

A `LinkedList` maintains a reference to its final node, so appending also takes \(O(1)\).

### **3.6 Insertion in the middle**

Suppose you want to insert `15` between `10` and `20`.

The list first needs to find the appropriate position.

Finding an element by index requires traversal.

Only after finding the relevant node can its links be changed in constant time.

Therefore:

- Finding the position: \(O(n)\).
- Updating references: \(O(1)\).
- Overall indexed insertion: \(O(n)\).

An insertion using an already-positioned `ListIterator` can be \(O(1)\), because the list does not need to search again.

### **3.7 LinkedList time complexity**

| Operation        | Time complexity |
| ---------------- | --------------- |
| Add at beginning | \(O(1)\)        |
| Add at end       | \(O(1)\)        |
| Remove first     | \(O(1)\)        |
| Remove last      | \(O(1)\)        |
| Get by index     | \(O(n)\)        |
| Search by value  | \(O(n)\)        |
| Insert at index  | \(O(n)\)        |
| Remove at index  | \(O(n)\)        |

### **3.8 ArrayList vs LinkedList**

| Feature             | ArrayList            | LinkedList          |
| ------------------- | -------------------- | ------------------- |
| Internal structure  | Dynamic array        | Doubly linked nodes |
| Index access        | \(O(1)\)             | \(O(n)\)          |
| Add at end          | Amortized \(O(1)\)   | \(O(1)\)          |
| Add at beginning    | \(O(n)\)             | \(O(1)\)          |
| Remove at beginning | \(O(n)\)             | \(O(1)\)          |
| Memory overhead     | Usually lower        | Usually higher      |
| Cache locality      | Generally better     | Generally worse     |

### **Why can ArrayList outperform LinkedList?**

This is an important performance concept.

An `ArrayList` stores references in a compact array. When traversing it, the processor can often access nearby memory efficiently.

A `LinkedList` stores nodes as separate objects. The next node may be located somewhere else in memory.

This creates additional pointer chasing and can lead to cache misses.

Therefore, even when a linked list offers \(O(1)\) insertion at a known position, it may still perform worse in real applications.

**Practical rule:** Choose `ArrayList` by default. Use `LinkedList` when its end-insertion/removal behaviour or list-iterator operations provide a genuine advantage.

Also consider `ArrayDeque` for queue and stack operations. It is usually a better choice than `LinkedList` for those purposes.

## **4. HashMap Internals**

This is one of the most important Java topics for interviews and real development.

### **4.1 What is HashMap?**

`HashMap` stores data as key-value pairs.

```
Map<Integer, String> students = new HashMap<>();

students.put(101, "Amit");
students.put(102, "Rahul");
students.put(103, "Priya");

System.out.println(students.get(102));
```

Output:

```
Rahul
```

A `HashMap` provides efficient key-based insertion, retrieval, and deletion on average.

### **4.2 How does HashMap work internally?**

A HashMap uses a hash table.

The basic process is:

1. Receive a key.
2. Calculate the key's hash code.
3. Transform the hash into a bucket index.
4. Find the corresponding bucket.
5. Search that bucket if it contains multiple entries.
6. Insert or retrieve the relevant value.

Consider:

```
Map<String, Integer> marks = new HashMap<>();

marks.put("Amit", 90);
```

Conceptually:

```
Key: "Amit"
       |
       v
hashCode()
       |
       v
Hash calculation
       |
       v
Bucket index
       |
       v
Store key-value entry
```

### **4.3 What is a hash function?**

A hash function converts a key into an integer-like hash value.

Java objects provide:

```
key.hashCode();
```

For strings, Java calculates a hash based on the characters.

For example:

```
String name = "Amit";

System.out.println(name.hashCode());
```

A HashMap uses the hash value to decide where an entry should be placed.

The hash code is not necessarily unique.

Two different keys can produce the same hash code.

This leads to collisions.

### **4.4 How does HashMap calculate a bucket index?**

In common OpenJDK implementations, HashMap first spreads the hash bits:

```
int hash = key.hashCode();

hash = hash ^ (hash >>> 16);
```

It then calculates the bucket index using:

```
int index = (capacity - 1) & hash;
```

The capacity is maintained as a power of two in this implementation.

The bit operation helps distribute hash values across the available buckets.

You generally do not need to implement this calculation yourself, but you should understand its purpose.

### **4.5 What is a hash collision?**

A collision occurs when different keys map to the same bucket.

Example:

```
HashMap buckets:

Bucket 0 → Entry
Bucket 1 → Entry → Entry
Bucket 2 → Empty
Bucket 3 → Entry
```

Two entries in Bucket 1 collided.

HashMap must handle this situation correctly.

### **4.6 Collision handling: Separate chaining**

HashMap stores entries in buckets.

When multiple entries occupy the same bucket, they can be connected as nodes.

Conceptually:

**Hash collisions**

**Bucket 0**

A → null

**Bucket 1**

B → C → D → null

**Bucket 2**

Empty

To locate a key, HashMap searches the bucket and checks whether the key matches.

It uses hash values and equality comparisons, including `equals()`.

### **4.7 Treeification: When does a bucket become a tree?**

In modern OpenJDK HashMap implementations, a heavily populated bucket can be converted from a linked structure into a balanced tree.

This is called **treeification**.

Why?

Searching through a long linked chain can require \(O(n)\) time.

A balanced tree can reduce that search to approximately \(O(\log n)\).

Common OpenJDK implementation thresholds include:

- A treeification threshold of 8 entries.
- A minimum table capacity of 64 before treeification is preferred.
- A bucket may be converted back to a linked structure when it becomes sufficiently small.

These are implementation details, not guarantees of the `Map` interface.

### **4.8 HashMap resizing and load factor**

HashMap maintains a load factor.

The load factor determines how full the table can become before resizing is triggered.

The default load factor is:

\[ 0.75 \]

The threshold is approximately:

\[ \text{Threshold}=\text{Capacity}\times\text{Load Factor} \]

For example:

\[ 16\times0.75=12 \]

When the size exceeds the threshold, HashMap resizes the table.

This involves allocating a larger table and redistributing entries.

Resizing is expensive, but it does not happen after every insertion.

### **4.9 Why are hashCode() and equals() important?**

Consider a custom class:

```
class Student {

    int id;

    Student(int id) {
        this.id = id;
    }
}
```

Now:

```
Student s1 = new Student(101);
Student s2 = new Student(101);

Map<Student, String> students = new HashMap<>();

students.put(s1, "Amit");

System.out.println(students.get(s2));
```

You might expect `"Amit"` because both students have the same ID.

But the default implementation of `equals()` checks object identity, so `s1` and `s2` are not equal.

We need to define equality.

```
import java.util.Objects;

class Student {

    int id;

    Student(int id) {
        this.id = id;
    }

    @Override
    public boolean equals(Object obj) {

        if (this == obj) {
            return true;
        }

        if (!(obj instanceof Student other)) {
            return false;
        }

        return id == other.id;
    }

    @Override
    public int hashCode() {
        return Objects.hash(id);
    }
}
```

Now HashMap can correctly recognize logically equivalent students.

**The contract:**

If two objects are equal according to `equals()`, they must return the same `hashCode()`.

The reverse is not required: two unequal objects can have the same hash code.

### **4.10 Why should HashMap keys generally be immutable?**

Consider:

```
class Student {

    int id;

    Student(int id) {
        this.id = id;
    }
}
```

Suppose `hashCode()` depends on `id`.

You insert a student with ID `101`, then change its ID to `202`.

The object may now produce a different hash code.

However, the entry is still located in the bucket selected by the original hash calculation.

A lookup using the modified key may fail.

Therefore, use stable, immutable fields for key equality and hashing.

### **4.11 HashMap complexity**

| Operation       | Average      | Worst-case idea                   |
| --------------- | ------------ | --------------------------------- |
| `put()`         | \(O(1)\)   | Can degrade                       |
| `get()`         | \(O(1)\)   | \(O(n)\) in adverse cases       |
| `remove()`      | \(O(1)\)   | Can degrade                       |
| `containsKey()` | \(O(1)\)   | Can degrade                       |
| Iteration       | \(O(n+c)\) | Depends on table size and entries |

Here, \(c\) represents table capacity.

Tree bins can improve collision-heavy bucket operations, but you should not treat every HashMap operation as guaranteed \(O(1)\).

### **4.12 When should you use HashMap?**

Use HashMap when you need:

- Fast key-based lookup.
- Frequency counting.
- Caching.
- Indexing records by IDs.
- Mapping one object to another.
- Counting occurrences of elements.

Example: Frequency counting.

```
import java.util.*;

public class Main {

    public static void main(String[] args) {

        int[] numbers = {1, 2, 2, 3, 3, 3};

        Map<Integer, Integer> frequency = new HashMap<>();

        for (int number : numbers) {

            frequency.put(
                number,
                frequency.getOrDefault(number, 0) + 1
            );
        }

        System.out.println(frequency);
    }
}
```

Output:

```
{1=1, 2=2, 3=3}
```

An alternative is:

```
frequency.merge(number, 1, Integer::sum);
```

This is useful in production code because it expresses the frequency update directly.

## **5. TreeMap and TreeSet**

### **5.1 What is TreeMap?**

`TreeMap` implements the `NavigableMap` interface.

It stores keys in sorted order.

Unlike HashMap, it does not use a hash table. Common Java implementations use a self-balancing red-black tree.

```
Map<Integer, String> students = new TreeMap<>();

students.put(103, "Priya");
students.put(101, "Amit");
students.put(102, "Rahul");

System.out.println(students);
```

Output:

```
{101=Amit, 102=Rahul, 103=Priya}
```

The keys are sorted naturally.

### **5.2 What is a Red-Black Tree?**

A red-black tree is a self-balancing binary search tree.

It maintains balancing rules so that the tree does not become excessively tall.

Important properties include:

1. Every node is red or black.
2. The root is black.
3. Red nodes cannot have red children.
4. Every path from a node to its descendant null leaves has the same number of black nodes.
5. The tree uses rotations and recoloring to restore its properties after updates.

These rules keep the tree height logarithmic relative to the number of elements.

### **5.3 TreeMap operations**

```
TreeMap<Integer, String> map = new TreeMap<>();

map.put(10, "A");
map.put(30, "B");
map.put(20, "C");

System.out.println(map.firstKey());

System.out.println(map.lastKey());

System.out.println(map.lowerKey(20));

System.out.println(map.higherKey(20));

System.out.println(map.floorKey(25));

System.out.println(map.ceilingKey(25));
```

Output:

```
10
30
10
30
20
30
```

Understand these navigation methods:

| Method          | Meaning                                   |
| --------------- | ----------------------------------------- |
| `firstKey()`    | Smallest key                              |
| `lastKey()`     | Largest key                               |
| `lowerKey(k)`   | Greatest key strictly smaller than `k`    |
| `higherKey(k)`  | Smallest key strictly greater than `k`    |
| `floorKey(k)`   | Greatest key less than or equal to `k`    |
| `ceilingKey(k)` | Smallest key greater than or equal to `k` |

### **5.4 TreeMap complexity**

| Operation      | Time                                      |
| -------------- | ----------------------------------------- |
| Insert         | \(O(\log n)\)                           |
| Search         | \(O(\log n)\)                           |
| Remove         | \(O(\log n)\)                           |
| First/last key | \(O(\log n)\) in common implementations |
| Iteration      | \(O(n)\)                                |

### **5.5 What is TreeSet?**

`TreeSet` stores unique elements in sorted order.

```
TreeSet<Integer> numbers = new TreeSet<>();

numbers.add(50);
numbers.add(10);
numbers.add(30);
numbers.add(10);

System.out.println(numbers);
```

Output:

```
[10, 30, 50]
```

Internally, a common implementation uses a `TreeMap` to store the elements as keys.

### **5.6 Important comparison: HashSet vs TreeSet**

| Feature        | HashSet             | TreeSet         |
| -------------- | ------------------- | --------------- |
| Data structure | Hash table          | Red-black tree  |
| Duplicates     | Not allowed         | Not allowed     |
| Ordering       | No guaranteed order | Sorted order    |
| Add            | Average \(O(1)\)    | \(O(\log n)\) |
| Search         | Average \(O(1)\)    | \(O(\log n)\) |
| Remove         | Average \(O(1)\)    | \(O(\log n)\) |

A `TreeSet` determines uniqueness using comparison: if the comparator returns zero, the elements are treated as the same set element.

This means the comparator should be consistent with `equals()` when you want standard `Set` equality semantics.

**When to use:**

- HashSet: When you need uniqueness and fast membership checks.
- TreeSet: When you need uniqueness and sorted navigation.

## **6. PriorityQueue Implementation**

### **6.1 What is PriorityQueue?**

A priority queue processes elements according to priority rather than simply the order in which they were inserted.

Java's `PriorityQueue` is commonly implemented using a binary heap.

By default, it is a min-heap.

This means the smallest element has the highest priority and is at the root.

```
PriorityQueue<Integer> pq = new PriorityQueue<>();

pq.add(40);
pq.add(10);
pq.add(30);
pq.add(20);

System.out.println(pq.peek());
```

Output:

```
10
```

### **6.2 What is a Binary Heap?**

A binary heap is a complete binary tree.

A min-heap follows this property:

\[ Parent \leq Children \]

Every parent is smaller than or equal to its children.

Example:

**Min-heap**

The smallest item is at the root. Every parent is no greater than its children.

### **6.3 How does insertion work?**

Suppose you insert `5` into a heap:

```
Before:

       10
      /  \
    20    30
```

The new item is initially placed at the next available leaf position.

```
       10
      /  \
    20    30
   /
  5
```

The heap property is violated because `5` is smaller than its parent.

The heap performs **heapify-up** (also called sift-up).

It swaps `5` with `20`, then with `10`.

```
       5
      / \
    10   30
   /
  20
```

The heap is now valid.

This takes \(O(\log n)\).

### **6.4 How does removal work?**

When you remove the minimum element:

```
pq.poll();
```

The root is removed.

The final element is moved to the root, and the heap performs heapify-down to restore the ordering.

This also takes \(O(\log n)\).

### **6.5 PriorityQueue complexity**

| Operation           | Time            |
| ------------------- | --------------- |
| `peek()`            | \(O(1)\)        |
| `offer()` / `add()` | \(O(\log n)\) |
| `poll()`            | \(O(\log n)\) |
| `remove(Object)`    | \(O(n)\)        |
| `contains(Object)`  | \(O(n)\)        |

Important: Iterating over a PriorityQueue does **not** guarantee sorted order. Only the head element has the priority guarantee.

To process all elements in priority order:

```
while (!pq.isEmpty()) {
    System.out.println(pq.poll());
}
```

### **6.6 Creating a max-heap**

Use a reverse comparator:

```
PriorityQueue<Integer> maxHeap =
    new PriorityQueue<>(Collections.reverseOrder());

maxHeap.add(10);
maxHeap.add(50);
maxHeap.add(20);

System.out.println(maxHeap.poll());
```

Output:

```
50
```

### **6.7 Where is PriorityQueue used?**

- Finding the smallest or largest element.
- Top-K problems.
- Scheduling tasks by priority.
- Dijkstra's shortest-path algorithm.
- Merging K sorted lists.
- Event-driven simulations.

## **7. Concurrent Collections Introduction**

### **7.1 What is a concurrent collection?**

A concurrent collection is designed to support access from multiple threads safely.

Consider a shared `ArrayList`:

```
List<Integer> numbers = new ArrayList<>();
```

Now imagine that two threads modify it simultaneously.

Both threads might try to change its internal state at the same time.

This can cause inconsistent behaviour, lost updates, or other concurrency problems.

Regular collections such as `ArrayList`, `HashMap`, and `HashSet` are not inherently thread-safe.

### **7.2 ConcurrentHashMap**

`ConcurrentHashMap` is designed for concurrent access.

```
ConcurrentHashMap<Integer, String> map =
    new ConcurrentHashMap<>();

map.put(101, "Amit");
map.put(102, "Rahul");
```

Multiple threads can access and update it without requiring you to synchronize every operation manually.

Modern OpenJDK implementations use techniques such as:

- Compare-and-set (CAS).
- Fine-grained synchronization.
- Volatile memory access.
- Coordination at the bucket level.

It is not simply a single globally synchronized HashMap.

Example:

```
import java.util.concurrent.*;

public class Main {

    public static void main(String[] args) {

        ConcurrentHashMap<String, Integer> counter =
            new ConcurrentHashMap<>();

        counter.put("visits", 0);

        counter.merge("visits", 1, Integer::sum);

        System.out.println(counter.get("visits"));
    }
}
```

### **7.3 Concurrent collection types**

| Collection            | Purpose                                 |
| --------------------- | --------------------------------------- |
| ConcurrentHashMap     | Concurrent key-value access             |
| CopyOnWriteArrayList  | Read-heavy lists with infrequent writes |
| CopyOnWriteArraySet   | Read-heavy sets                         |
| ConcurrentLinkedQueue | Non-blocking concurrent queue           |
| BlockingQueue         | Producer-consumer coordination          |
| ConcurrentSkipListMap | Concurrent sorted map                   |
| ConcurrentSkipListSet | Concurrent sorted set                   |

### **7.4 CopyOnWriteArrayList**

CopyOnWriteArrayList is useful when reads are frequent and modifications are relatively rare.

Its approach is:

1. A reader accesses the current array.
2. A writer creates a new copy of the array.
3. The writer modifies the new array.
4. The new array becomes the current one.

This makes reads efficient but writes expensive.

```
CopyOnWriteArrayList<String> names =
    new CopyOnWriteArrayList<>();

names.add("Amit");
names.add("Rahul");
```

### **7.5 BlockingQueue**

BlockingQueue is commonly used in producer-consumer systems.

A producer creates tasks and places them into a queue. A consumer removes and processes them.

```
BlockingQueue<String> tasks =
    new ArrayBlockingQueue<>(5);
```

The queue has a maximum capacity of five.

A producer can wait when the queue is full, and a consumer can wait when the queue is empty.

### **7.6 Important concurrent collection differences**

| Feature          | ArrayList           | CopyOnWriteArrayList   |
| ---------------- | ------------------- | ---------------------- |
| Thread-safe      | No                  | Yes                    |
| Read operations  | Fast                | Fast                   |
| Write operations | Usually inexpensive | Copies the array       |
| Best use case    | General use         | Many reads, few writes |

**When should you use ConcurrentHashMap?**

When multiple threads need to access and modify a shared key-value structure.

For example, an application-wide request counter, concurrent cache, or shared lookup table.

Remember that thread-safe individual operations do not automatically make a sequence of several operations atomic. Use appropriate atomic methods such as `compute`, `merge`, and `putIfAbsent`, or additional synchronization when required.

# **PART 2 — JVM MEMORY AND EXECUTION**

## **8. Java Memory Model**

### **8.1 What is the Java Memory Model?**

The Java Memory Model (JMM) defines how threads interact through memory.

It establishes rules for:

- Visibility.
- Atomicity.
- Ordering.
- Synchronization.
- Communication between threads.

To understand this, first understand what can go wrong when multiple threads share data.

### **8.2 The visibility problem**

Consider:

```
class SharedData {

    boolean running = true;

    public void stop() {
        running = false;
    }
}
```

Suppose one thread executes:

```
while (sharedData.running) {

}
```

Another thread executes:

```
sharedData.stop();
```

You might expect the first thread to observe the updated value immediately.

But without appropriate synchronization, there is no guaranteed visibility relationship between the two threads.

The threads may not observe each other's changes as you expect.

This is a **visibility problem**.

### **8.3 Using volatile**

Declare the shared variable as `volatile`.

```
class SharedData {

    volatile boolean running = true;

    public void stop() {
        running = false;
    }
}
```

A volatile write happens-before subsequent reads of that same variable under the JMM rules.

This gives the required visibility and ordering guarantees for this flag example.

However, volatile does not make every operation atomic.

### **8.4 Atomicity problem**

Consider:

```
volatile int counter = 0;

counter++;
```

You might think this is one operation.

It is actually a read-modify-write sequence:

1. Read the current value.
2. Add one.
3. Write the new value.

If two threads execute it simultaneously, one update can be lost.

For atomic increments, use `AtomicInteger`:

```
import java.util.concurrent.atomic.AtomicInteger;

AtomicInteger counter = new AtomicInteger(0);

counter.incrementAndGet();
```

### **8.5 Using synchronized**

`synchronized` provides mutual exclusion and memory visibility through monitor lock rules.

```
class Counter {

    private int count = 0;

    public synchronized void increment() {
        count++;
    }

    public synchronized int getCount() {
        return count;
    }
}
```

Only one thread can execute a synchronized instance method on the same object monitor at a time.

When a thread exits a synchronized block, its unlock happens-before a subsequent lock of that same monitor.

### **8.6 Happens-before relationship**

Happens-before is a relationship that establishes ordering and visibility between operations.

Important examples include:

- Unlocking a monitor happens-before a later lock on the same monitor.
- A volatile write happens-before a subsequent read of that same volatile variable.
- Calling `Thread.start()` happens-before actions in the started thread.
- Actions in a thread happen-before another thread successfully returns from `join()` on it.
- Program order inside a single thread establishes ordering between its operations.

### **8.7 Immutable objects and thread safety**

An immutable object cannot have its observable state changed after construction.

Example:

```
public final class Student {

    private final int id;

    private final String name;

    public Student(int id, String name) {
        this.id = id;
        this.name = name;
    }

    public int getId() {
        return id;
    }

    public String getName() {
        return name;
    }
}
```

The class:

- Is declared `final`.
- Uses private fields.
- Uses final fields.
- Does not provide setters.
- Does not expose mutable internal state.

Immutable objects are easier to share between threads because their state cannot be modified after construction.

**Important:** An immutable object must not expose mutable internal objects that can be changed through another reference. Defensive copying may be required.

### **8.8 JMM summary**

| Concept           | Purpose                               |
| ----------------- | ------------------------------------- |
| Volatile          | Visibility and ordering               |
| Synchronized      | Mutual exclusion and visibility       |
| AtomicInteger     | Atomic integer operations             |
| Happens-before    | Defines ordering and visibility       |
| Immutable objects | Avoid state modification              |
| Locks             | Coordinate access to shared resources |

The most important distinction:

- Visibility means one thread can observe another thread's update.
- Atomicity means an operation happens as one indivisible unit.
- Ordering means operations obey the required execution constraints.

These are related, but they are not the same thing.

## **9. Stack and Heap Memory**

The JVM uses several runtime memory areas. Two of the most important are the Java thread stacks and the heap.

### **9.1 Stack memory**

Every thread has its own JVM stack.

The stack stores method frames.

A method frame typically contains:

- Local variables.
- An operand stack.
- Information used for method execution.
- Return and linking information.

Consider:

```
public class Main {

    public static void main(String[] args) {

        int x = 10;

        int y = 20;

        int result = add(x, y);

        System.out.println(result);
    }

    static int add(int a, int b) {

        return a + b;
    }
}
```

When `main()` calls `add()`, a new method frame is created for `add()`.

When `add()` returns, its frame is removed.

Conceptually:

**Thread stack**

main() frame

x = 10, y = 20, result = ...

add() frame

a = 10, b = 20

Method calls create frames as execution enters them. Frames are removed as methods return.

### **9.2 Stack overflow**

Because stack memory has a limit, extremely deep recursion can cause `StackOverflowError`.

```
public class Main {

    static void recursive() {

        recursive();
    }

    public static void main(String[] args) {

        recursive();
    }
}
```

This method never reaches a base case.

It keeps calling itself until the thread's stack cannot accommodate additional frames.

### **9.3 Heap memory**

The heap is the main runtime area where Java objects and arrays are allocated.

The heap is generally shared across threads.

Example:

```
Student student = new Student(101, "Amit");
```

The object is normally allocated on the heap.

The local variable `student` holds a reference to the object.

A conceptual view:

**Stack and heap**

**Stack**

student

Reference

**Heap**

Student object

id = 101

name = "Amit"

Reference points to the object

Do not confuse the reference with the object.

They are different things.

Also, avoid memorizing an oversimplified rule such as "all local variables are on the stack."

The actual placement and optimization of values depends on JVM execution and compiler optimizations. Local variables may be represented in registers or optimized away, and object allocations may sometimes be eliminated.

### **9.4 Other JVM memory areas**

| Memory area                   | Purpose                                   |
| ----------------------------- | ----------------------------------------- |
| Heap                          | Objects and arrays                        |
| Java stacks                   | Method frames for each thread             |
| Program Counter (PC) register | Tracks the current instruction per thread |
| Method area                   | Runtime class and method information      |
| Native method stacks          | Supports native method execution          |
| Metaspace in HotSpot          | Stores class metadata in native memory    |

The method area is part of the JVM specification's runtime data-area model. Metaspace is a HotSpot implementation of class metadata storage.

### **9.5 Stack vs heap**

| Feature                | Stack              | Heap                              |
| ---------------------- | ------------------ | --------------------------------- |
| Ownership              | Per thread         | Shared                            |
| Stores                 | Method frames      | Objects and arrays                |
| Lifecycle              | Method-frame based | Garbage collected                 |
| Typical access pattern | Method execution   | Object references                 |
| Main issue             | Stack overflow     | Heap exhaustion / memory pressure |

## **10. Garbage Collection**

### **10.1 What is Garbage Collection?**

Garbage Collection (GC) is the JVM's automatic memory-management process.

It identifies objects that are no longer reachable and reclaims the memory they occupy.

Example:

```
public class Main {

    public static void main(String[] args) {

        Student student = new Student(101);

        student = null;
    }
}
```

After the reference is set to `null`, the object may become eligible for garbage collection if no other reachable references point to it.

It is not necessarily collected immediately.

### **10.2 How does garbage collection determine what can be removed?**

The JVM uses reachability analysis.

It begins with references called **GC roots**.

Common root categories include:

- References in active thread stacks.
- References from static fields.
- References held by JNI/native code.
- Other runtime references recognized as roots.

The collector follows references from these roots.

Objects reachable through that reference graph are considered live.

Objects that cannot be reached are eligible for collection.

### **10.3 Generational garbage collection**

Many JVM garbage collectors use generational ideas because many objects tend to have short lifetimes.

The heap is conceptually divided into:

- Young generation.
- Old generation.

The young generation often includes Eden and survivor spaces in generational collectors.

**Generational heap model**

**Young generation**

Eden

Survivor 0

Survivor 1

Objects that survive enough collections may be promoted

**Old generation**

Longer-lived objects

Conceptual generational layout. The exact heap organization depends on the selected garbage collector.

A typical lifecycle:

1. A new object is allocated.
2. It is initially placed in a young region in a generational collector.
3. If it becomes unreachable, it can be reclaimed.
4. If it survives collections, it may be promoted.
5. Old-generation collections manage longer-lived objects.

### **10.4 Garbage collection algorithms**

**Mark-and-sweep**

1. Mark reachable objects.
2. Identify unmarked objects.
3. Reclaim their memory.

**Mark-and-compact**

1. Mark live objects.
2. Move them together.
3. Reclaim fragmented space.

**Copying collection**

1. Identify live objects in a region.
2. Copy them into another region.
3. Reuse the original region.

Different collectors combine techniques differently.

### **10.5 Important Java garbage collectors**

| Collector   | General idea                                           |
| ----------- | ------------------------------------------------------ |
| Serial GC   | Single-threaded collection                             |
| Parallel GC | Uses multiple worker threads                           |
| G1 GC       | Divides heap into regions and targets pause-time goals |
| ZGC         | Designed for very low pause times                      |
| Shenandoah  | Uses concurrent techniques to reduce pauses            |

Their availability and defaults depend on the JVM distribution and version.

### **10.6 What is Stop-the-World?**

Some GC phases pause application threads.

This is called a Stop-the-World pause.

Suppose your application is processing requests:

```
Request 1 → processing
Request 2 → processing
GC pause → application threads paused
GC work completed
Request processing resumes
```

Long pauses can increase application latency.

Some collectors perform substantial work concurrently, but even low-pause collectors can have short pauses.

### **10.7 Memory leaks in Java**

Java has garbage collection, but Java applications can still experience memory leaks.

Why?

Because the GC cannot reclaim objects that are still reachable.

Example:

```
class Cache {

    static List<byte[]> data = new ArrayList<>();

    static void addData() {

        data.add(new byte[1024 * 1024]);
    }
}
```

Every call creates another array and stores it in a static list.

The list keeps references to all those arrays.

They remain reachable, so the garbage collector cannot reclaim them.

Common causes of memory leaks:

- Unbounded caches.
- Static collections retaining objects.
- Event listeners not removed.
- Unclosed resource-related references.
- Thread-local values retained longer than expected.
- Incorrect object lifecycle management.

### **10.8 Can you force garbage collection?**

You can request it:

```
System.gc();
```

But this is only a request. The JVM does not guarantee that a collection will occur at that exact time.

Do not use `System.gc()` as your normal application memory-management strategy.

### **10.9 Garbage collection is not resource management**

Files, sockets, and database connections are resources that should be closed explicitly.

Use try-with-resources:

```
import java.io.*;

public class Main {

    public static void main(String[] args)
            throws IOException {

        try (BufferedReader reader =
                 new BufferedReader(
                     new FileReader("data.txt"))) {

            System.out.println(reader.readLine());
        }
    }
}
```

The resource is closed when execution leaves the try block, even if an exception occurs.

**Key idea:** GC manages memory. It does not replace disciplined management of external resources.

## **11. JVM Architecture**

### **11.1 What is the JVM?**

The Java Virtual Machine is the runtime environment that executes Java bytecode.

Java source code is not directly executed as native processor instructions by the usual Java compilation process.

The flow is:

**Java source code**

Main.java

**Java compiler**

javac

**Bytecode**

Main.class

**JVM**

Class Loader

Runtime Areas

Interpreter

JIT Compiler

Garbage Collector

**Native machine instructions**

Executed by the processor

### **11.2 Main JVM components**

**1. Class Loader Subsystem**

Loads Java classes into the JVM.

**2. Runtime Data Areas**

Provide memory areas for execution.

These include:

- Heap.
- Java thread stacks.
- Program Counter registers.
- Method-area-related runtime structures.
- Native method stacks.

**3. Execution Engine**

Executes bytecode using:

- Interpreter.
- JIT compiler.
- Other runtime execution optimizations.

**4. Garbage Collector**

Reclaims memory occupied by unreachable objects.

**5. Native Interface and Libraries**

JNI and native libraries allow Java programs to interact with native code and platform capabilities.

### **11.3 JVM vs JRE vs JDK**

| Term | Meaning                                                           |
| ---- | ----------------------------------------------------------------- |
| JVM  | Executes bytecode                                                 |
| JRE  | Runtime components needed to run Java applications                |
| JDK  | Development kit containing tools such as the compiler and runtime |

A JDK provides the tools needed to compile and develop Java applications.

## **12. Class Loading**

### **12.1 What is class loading?**

Before the JVM can execute code from a class, the class must be loaded into the runtime.

For example:

```
Student student = new Student();
```

When the class is needed, the JVM ensures that it is loaded and initialized according to the class lifecycle rules.

### **12.2 Class loading lifecycle**

The broad lifecycle contains three main phases:

1. Loading.
2. Linking.
3. Initialization.

Linking itself includes verification, preparation, and resolution.

**Class lifecycle**

**1. Loading**

Find and create the class representation

**2. Linking**

**Verification**

Validate bytecode and structural correctness

**Preparation**

Allocate and initialize static storage to default values

**Resolution**

Resolve symbolic references when required

**3. Initialization**

Execute class initialization code and explicit static initializers

### **12.3 Class loaders**

The standard class-loader hierarchy commonly includes:

**1. Bootstrap ClassLoader**

Loads core Java runtime classes.

**2. Platform ClassLoader**

Loads platform classes.

**3. Application ClassLoader**

Loads application classes from the application class path and related sources.

### **12.4 Parent delegation model**

When a class loader receives a request, it generally delegates to its parent before attempting to load the class itself.

Why?

It helps avoid duplicate loading of core classes and maintains a consistent class-loading hierarchy.

A simplified process:

```
Application ClassLoader
          |
          v
Platform ClassLoader
          |
          v
Bootstrap ClassLoader
```

If the parent can load the class, its result is used. Otherwise, the child loader may try to load it itself.

There are specialized class-loading arrangements that can customize or depart from the usual delegation process.

### **12.5 Static initialization**

Consider:

```
class Student {

    static int count = 10;

    static {

        System.out.println("Class initialized");
    }
}
```

When the class is initialized, its static initialization code executes.

The class is initialized once per defining class loader, subject to JVM class-initialization rules.

A frequently used interview detail: reading a compile-time constant field does not necessarily trigger initialization of the declaring class.

## **13. JIT Compilation**

### **13.1 What is JIT?**

JIT stands for Just-In-Time compilation.

The JVM can compile frequently executed bytecode into native machine code while the program is running.

Why is this useful?

The interpreter can begin executing bytecode quickly, while the JIT compiler can optimize frequently executed sections based on runtime information.

### **13.2 Interpreter vs JIT**

**Interpreter**

Executes bytecode instructions.

Advantages:

- Can start execution quickly.
- Does not need to compile all code first.

**JIT compiler**

Compiles selected code into native instructions.

Advantages:

- Can optimize hot code paths.
- Can use information gathered during execution.
- Can reduce the overhead of repeated interpretation.

### **13.3 What are hot methods?**

A method that executes frequently is called a hot method.

Consider:

```
public class Main {

    static long calculate() {

        long total = 0;

        for (int i = 0; i < 1000000; i++) {

            total += i;
        }

        return total;
    }

    public static void main(String[] args) {

        for (int i = 0; i < 1000; i++) {
            calculate();
        }
    }
}
```

The JVM can gather runtime information about frequently executed methods and potentially compile them.

### **13.4 Tiered compilation**

In common HotSpot configurations, tiered compilation uses multiple execution and compilation levels.

A simplified view:

1. Start with interpretation.
2. Gather profiling information.
3. Use faster compilation levels for suitable methods.
4. Apply more advanced optimization for sufficiently hot code.

Historically, HotSpot includes compilers known as C1 and C2.

You should understand the concepts rather than assume every JVM uses exactly the same compilation strategy.

### **13.5 Important JIT optimizations**

**Method inlining**

Instead of executing a method call, the compiler may insert the method's instructions into the caller.

```
static int square(int x) {
    return x * x;
}
```

For a small, frequently called method, inlining may reduce call overhead and enable further optimizations.

**Escape analysis**

The JIT analyzes whether an object can be accessed outside a particular scope.

This information can enable optimizations such as scalar replacement.

**Dead-code elimination**

Code that has no observable effect may be removed.

**Loop optimizations**

The JIT may transform loops to improve execution.

**Deoptimization**

If assumptions made by optimized code become invalid, the JVM can fall back to less optimized execution and potentially recompile later.

### **13.6 Why does Java sometimes start slower and become faster?**

Because Java applications may require warm-up.

At the beginning, the JVM might interpret methods and collect runtime profiling information.

As the application runs, frequently executed code may be optimized and compiled.

This is important when benchmarking Java.

A benchmark that measures only the first execution may not represent the application's steady-state performance.

## **14. Java Performance Profiling**

### **14.1 What is profiling?**

Performance profiling is the process of examining how a program uses resources while running.

It helps answer:

- Which methods consume the most CPU?
- Which methods allocate the most memory?
- Why is garbage collection occurring frequently?
- Which threads are blocked?
- Why are requests taking too long?
- Is application performance degrading over time?

### **14.2 Important performance metrics**

| Metric          | What it tells you                            |
| --------------- | -------------------------------------------- |
| Latency         | How long an operation takes                  |
| Throughput      | Operations completed per unit of time        |
| CPU utilization | How much processor capacity is used          |
| Heap usage      | Amount of heap memory occupied               |
| Allocation rate | How quickly objects are allocated            |
| GC pause time   | Time application execution is paused         |
| Thread count    | Number of active threads                     |
| Contention      | How frequently threads compete for resources |

A system can have high throughput but poor latency for individual requests. You should measure both.

### **14.3 Profiling tools**

**Java Flight Recorder (JFR)**

A low-overhead event-recording framework included in modern JDKs.

It can capture information about:

- CPU usage.
- Allocation.
- Garbage collection.
- Thread activity.
- Lock contention.
- Runtime events.

**Java Mission Control (JMC)**

A graphical tool for analyzing JFR recordings.

**VisualVM**

A graphical monitoring and profiling tool that can inspect application performance, memory, and threads.

**jcmd**

A diagnostic utility for interacting with running JVM processes.

**jstack**

A tool for examining thread stacks and diagnosing deadlocks or blocked threads.

**jmap**

A tool associated with heap information and heap dumps.

**JMH**

Java Microbenchmark Harness. It is useful for writing controlled microbenchmarks.

### **14.4 Useful diagnostic commands**

Find Java processes:

```
jcmd -l
```

Display JVM information:

```
jcmd <PID> VM.version
```

Inspect thread stacks:

```
jcmd <PID> Thread.print
```

Inspect heap information:

```
jcmd <PID> GC.heap_info
```

Start a JFR recording:

```
jcmd <PID> JFR.start duration=60s filename=recording.jfr
```

The exact commands available depend on the JDK and runtime environment. You generally need the appropriate permissions to inspect a process.

### **14.5 Example: Finding a slow method**

Suppose your application responds slowly.

Do not immediately assume the algorithm is the problem.

Investigate:

1. Measure request latency.
2. Check CPU usage.
3. Record a profile.
4. Identify expensive methods.
5. Determine whether they are CPU-bound, blocked, or waiting on external services.
6. Optimize the actual bottleneck.
7. Measure again.

A method that appears slow in a single request might actually be spending its time waiting for a database rather than executing Java instructions.

### **14.6 Microbenchmarking with JMH**

A simple JMH benchmark can compare two approaches.

```
import org.openjdk.jmh.annotations.*;

import java.util.concurrent.TimeUnit;

@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@State(Scope.Thread)
public class ExampleBenchmark {

    int[] numbers;

    @Setup
    public void setup() {

        numbers = new int[1000];

        for (int i = 0; i < numbers.length; i++) {
            numbers[i] = i;
        }
    }

    @Benchmark
    public long calculateSum() {

        long sum = 0;

        for (int number : numbers) {
            sum += number;
        }

        return sum;
    }
}
```

JMH manages benchmark execution details such as warm-up, measurement iterations, and result collection.

Do not rely on a simple `System.nanoTime()` loop as a substitute for a proper benchmark. JVM warm-up, dead-code elimination, compilation, and garbage collection can distort results.

## **15. Object Allocation**

### **15.1 What is object allocation?**

Object allocation means creating a new object or array.

Example:

```
Student student = new Student(101, "Amit");
```

This creates an object and returns a reference to it.

A Java object commonly contains:

- Object header information.
- Instance fields.
- Alignment padding, if needed.

The precise layout depends on the JVM, object type, and runtime configuration.

### **15.2 Where are objects allocated?**

In a typical HotSpot JVM, objects are allocated on the heap.

However, allocation does not always mean the JVM must create a lasting heap object.

The JIT may optimize certain objects away using escape analysis and scalar replacement.

### **15.3 Thread Local Allocation Buffers (TLABs)**

To make allocation efficient, HotSpot commonly gives threads small allocation regions called TLABs.

A thread can allocate many objects inside its own buffer without requiring a global synchronization operation for every allocation.

This makes many small object allocations surprisingly inexpensive.

### **15.4 Excessive object allocation**

Consider:

```
String result = "";

for (int i = 0; i < 1000; i++) {

    result += i;
}
```

Repeated string concatenation inside a loop can create many intermediate strings.

A more suitable approach is:

```
StringBuilder result = new StringBuilder();

for (int i = 0; i < 1000; i++) {

    result.append(i);
}

String finalResult = result.toString();
```

`StringBuilder` is designed for efficient mutable string construction in a single-threaded context.

### **15.5 Boxing and unboxing**

Java collections store objects, not primitive values.

This means storing an `int` in a collection requires boxing.

```
List<Integer> numbers = new ArrayList<>();

numbers.add(10);
```

Conceptually, Java converts the primitive `int` into an `Integer` object.

Unboxing happens when extracting the value:

```
int number = numbers.get(0);
```

For ordinary code, this is convenient.

But in large numeric workloads, boxing can create unnecessary objects and overhead.

For performance-sensitive numeric processing, primitive arrays may be more efficient.

### **15.6 Object pooling**

Object pooling means reusing existing objects instead of creating new ones.

It can be useful for expensive resources, such as certain connection-management systems.

But pooling ordinary Java objects is not automatically a performance improvement.

Why?

- Modern JVM allocation is often inexpensive.
- Pools require management.
- Pooled objects may remain reachable longer.
- Synchronization can add overhead.
- Reuse can create state-management bugs.

Use pooling only when measurement shows that it helps.

## **16. Time and Memory Optimization**

Performance optimization is not just about reducing CPU instructions.

It is about choosing better algorithms, data structures, memory layouts, and execution strategies.

### **16.1 Choose the right data structure**

Suppose you need to check whether a student ID exists.

Approach 1: List.

```
List<Integer> ids = new ArrayList<>();

boolean exists = ids.contains(101);
```

Searching a list takes \(O(n)\).

Approach 2: HashSet.

```
Set<Integer> ids = new HashSet<>();

boolean exists = ids.contains(101);
```

Membership testing takes average \(O(1)\).

The second solution is generally better for repeated membership checks.

### **16.2 Avoid unnecessary nested loops**

Consider:

```
for (int i = 0; i < n; i++) {

    for (int j = 0; j < n; j++) {

        System.out.println(i + " " + j);
    }
}
```

This takes:

\[ O(n^2) \]

For \(n=10,000\), there are approximately 100 million inner-loop executions.

Algorithmic improvements usually matter more than minor syntax changes.

### **16.3 Reduce unnecessary copying**

Avoid repeatedly copying large collections.

For example:

```
List<Integer> copy = new ArrayList<>(original);
```

This can be useful when you need an independent copy, but copying large data structures unnecessarily consumes time and memory.

Understand whether you need:

- A view.
- A shallow copy.
- A deep copy.
- An immutable copy.
- A reference to the original object.

These choices have different semantics.

### **16.4 Use efficient input/output**

For large input:

```
import java.io.*;

public class Main {

    public static void main(String[] args)
            throws IOException {

        BufferedReader br =
            new BufferedReader(
                new InputStreamReader(System.in)
            );

        String line = br.readLine();

        System.out.println(line);
    }
}
```

Buffering reduces the cost of repeated underlying I/O operations.

For very large numeric input, a custom fast input parser may be useful, but it should be introduced only when needed.

### **16.5 Avoid unnecessary repeated computation**

Example:

```
for (int i = 0; i < list.size(); i++) {

    // Process list.get(i)
}
```

For an `ArrayList`, this is generally fine.

But for a `LinkedList`, repeated indexed access can result in \(O(n^2)\) traversal.

For a linked list, iteration is more appropriate:

```
for (Integer value : linkedList) {

    // Process value
}
```

This illustrates why understanding internal data structures matters.

### **16.6 Memory optimization techniques**

- Avoid retaining objects longer than needed.
- Use primitive types when object wrappers are unnecessary.
- Avoid unbounded collections and caches.
- Reuse expensive resources appropriately.
- Use streaming for large datasets rather than loading everything into memory.
- Prefer appropriate data structures over unnecessarily complicated ones.
- Close files, streams, sockets, and database resources.

### **16.7 Time vs memory trade-offs**

Sometimes faster algorithms consume more memory.

For example, using a HashSet to remember previously visited values:

- Adds additional memory usage.
- Can reduce repeated searching time.

This is a common time-space trade-off.

You should choose based on the input size, constraints, and application requirements.

## **17. Big-O vs Practical Performance**

Understanding complexity is necessary, but it does not tell the entire performance story.

Two operations can have the same Big-O complexity and still have very different execution times.

### **17.1 What does Big-O tell us?**

Big-O describes how the cost of an algorithm grows as input size increases.

For example:

| Complexity       | Growth pattern | Common example               |
| ---------------- | -------------- | ---------------------------- |
| \(O(1)\)       | Constant       | Array index access           |
| \(O(\log n)\)  | Logarithmic    | Binary search                |
| \(O(n)\)       | Linear         | List traversal               |
| \(O(n\log n)\) | Linearithmic   | Efficient comparison sorting |
| \(O(n^2)\)     | Quadratic      | Two nested loops             |
| \(O(2^n)\)     | Exponential    | Some brute-force searches    |

### **17.2 Why isn't Big-O enough?**

Consider these two operations:

- Accessing an element in an ArrayList.
- Accessing an element in an array.

Both provide \(O(1)\) indexed access.

However, their implementation details and constant costs differ.

Similarly:

- ArrayList iteration is \(O(n)\).
- LinkedList iteration is \(O(n)\).

But ArrayList often performs better because of memory locality and fewer object dereferences.

### **17.3 Important practical performance factors**

**1. Constant factors**

An operation with a small constant factor may be faster for realistic input sizes.

**2. Cache locality**

Sequential memory access can be faster than scattered memory access.

**3. Allocation overhead**

Creating and discarding many objects can increase allocation and garbage-collection pressure.

**4. Memory usage**

A data structure can be theoretically fast but consume excessive memory.

**5. CPU branch behaviour**

Unpredictable branching can affect processor performance.

**6. I/O**

Disk, database, network, and console operations can dominate CPU execution time.

### **17.4 Practical data structure comparison**

| Structure     | Lookup                                   | Insertion                   | Ordering            |
| ------------- | ---------------------------------------- | --------------------------- | ------------------- |
| ArrayList     | \(O(n)\) by value; \(O(1)\) by index | Amortized \(O(1)\) at end | Insertion order     |
| LinkedList    | \(O(n)\)                               | \(O(1)\) at known node    | Insertion order     |
| HashSet       | Average \(O(1)\)                       | Average \(O(1)\)          | No guaranteed order |
| TreeSet       | \(O(\log n)\)                          | \(O(\log n)\)             | Sorted              |
| HashMap       | Average \(O(1)\) by key                | Average \(O(1)\)          | No guaranteed order |
| TreeMap       | \(O(\log n)\) by key                   | \(O(\log n)\)             | Sorted by key       |
| PriorityQueue | \(O(1)\) for head                      | \(O(\log n)\)             | Priority at head    |

### **17.5 Example: Searching a million values**

Suppose you need to perform 100,000 membership checks against one million values.

With an ArrayList:

```
boolean found = numbers.contains(target);
```

Each search may examine up to one million elements.

With a HashSet:

```
boolean found = numberSet.contains(target);
```

Each lookup takes average constant time under ordinary hashing assumptions.

Building the HashSet has a cost and requires additional memory, but repeated lookups can make the trade-off worthwhile.

**Important lesson:** Analyze the entire workload, not just one individual operation.

## **18. Writing Efficient Java Code**

Now combine everything into practical engineering rules.

### **18.1 Select data structures based on the task**

| Requirement                        | Suitable structure   |
| ---------------------------------- | -------------------- |
| Frequent indexed access            | ArrayList            |
| Unique values                      | HashSet              |
| Fast key lookup                    | HashMap              |
| Sorted keys                        | TreeMap              |
| Sorted unique values               | TreeSet              |
| Repeated minimum/maximum retrieval | PriorityQueue        |
| Queue or stack operations          | ArrayDeque           |
| Concurrent key-value access        | ConcurrentHashMap    |
| Many reads, few writes             | CopyOnWriteArrayList |

### **18.2 Prefer interfaces for variable declarations**

Instead of:

```
ArrayList<String> names = new ArrayList<>();
```

Prefer:

```
List<String> names = new ArrayList<>();
```

Why?

The variable depends on the interface rather than the concrete implementation.

You can later change the implementation without changing code that uses the `List` interface.

### **18.3 Use the correct collection methods**

Prefer:

```
map.getOrDefault(key, 0);
```

Instead of manually checking for key existence every time.

Use:

```
map.merge(key, 1, Integer::sum);
```

For frequency counting.

Use:

```
set.add(value);
```

To test uniqueness while inserting.

Use:

```
queue.offer(value);
```

For queue insertion where the queue may have capacity restrictions.

### **18.4 Avoid inefficient string concatenation inside loops**

Less efficient for repeated concatenation:

```
String result = "";

for (int i = 0; i < 1000; i++) {
    result += i;
}
```

Better:

```
StringBuilder result = new StringBuilder();

for (int i = 0; i < 1000; i++) {
    result.append(i);
}
```

### **18.5 Avoid unnecessary object creation**

Do not create new objects repeatedly when they serve no purpose.

For example, calculate reusable values outside a loop when doing so preserves the intended behaviour.

But do not introduce complicated reuse or object pooling without profiling.

### **18.6 Write algorithms with complexity in mind**

Suppose you need to find duplicates in an array.

A nested-loop solution:

```
for (int i = 0; i < numbers.length; i++) {

    for (int j = i + 1; j < numbers.length; j++) {

        if (numbers[i] == numbers[j]) {
            System.out.println(numbers[i]);
        }
    }
}
```

Time complexity:

\[ O(n^2) \]

A HashSet-based solution:

```
import java.util.*;

public class Main {

    public static void main(String[] args) {

        int[] numbers = {1, 2, 3, 2, 4, 3};

        Set<Integer> seen = new HashSet<>();

        Set<Integer> duplicates = new HashSet<>();

        for (int number : numbers) {

            if (!seen.add(number)) {

                duplicates.add(number);
            }
        }

        System.out.println(duplicates);
    }
}
```

Average time complexity:

\[ O(n) \]

Additional space complexity:

\[ O(n) \]

The second solution trades memory for better average execution time.

### **18.7 Use profiling before optimizing**

A professional performance workflow is:

1. **Establish a baseline**

   Measure the application's current latency, throughput, memory consumption, and CPU usage.
2. **Identify the bottleneck**

   Use profiling, thread analysis, heap information, or database tracing to locate the expensive operation.
3. **Understand the cause**

   Determine whether the issue is algorithmic, memory-related, concurrency-related, or caused by external I/O.
4. **Apply a targeted improvement**

   Change the algorithm, collection, memory behaviour, or synchronization strategy.
5. **Measure again**

   Compare results against the original baseline and check that correctness has not changed.

The goal is not to write the shortest code or use the fewest objects. The goal is to build code that is correct, maintainable, and efficient for its actual workload.

# **PART 4 — WORKED EXAMPLES**

## **Example 1: Find the K largest elements using PriorityQueue**

**Problem:** Given an array, return the three largest elements.

Input:

```
[10, 5, 20, 8, 15, 30]
```

Expected result:

```
[30, 20, 15]
```

### **Approach**

Maintain a min-heap with at most `k` elements.

Whenever the heap becomes larger than `k`, remove its smallest element.

At the end, the heap contains the `k` largest values.

```
import java.util.*;

public class Main {

    public static List<Integer> largestK(int[] numbers, int k) {

        if (k < 0 || k > numbers.length) {
            throw new IllegalArgumentException("Invalid k");
        }

        PriorityQueue<Integer> minHeap =
            new PriorityQueue<>();

        for (int number : numbers) {

            minHeap.offer(number);

            if (minHeap.size() > k) {

                minHeap.poll();
            }
        }

        List<Integer> result = new ArrayList<>();

        while (!minHeap.isEmpty()) {
            result.add(minHeap.poll());
        }

        Collections.reverse(result);

        return result;
    }

    public static void main(String[] args) {

        int[] numbers = {10, 5, 20, 8, 15, 30};

        System.out.println(largestK(numbers, 3));
    }
}
```

Output:

```
[30, 20, 15]
```

**Complexity:**

- Time: \(O(n\log k)\).
- Extra space: \(O(k)\).

This is useful when `k` is much smaller than the total input size.

## **Example 2: Build a student lookup system with HashMap**

**Problem:** Store student IDs and names, then find a student using their ID.

```
import java.util.*;

public class Main {

    public static void main(String[] args) {

        Map<Integer, String> students = new HashMap<>();

        students.put(101, "Amit");
        students.put(102, "Rahul");
        students.put(103, "Priya");

        int searchId = 102;

        String name = students.get(searchId);

        if (name != null) {

            System.out.println("Student: " + name);

        } else {

            System.out.println("Student not found");
        }
    }
}
```

Average lookup time:

\[ O(1) \]

This pattern is useful in student management systems, employee directories, database indexing layers, and caches.

## **Example 3: Find the first non-repeating character**

**Problem:** Given a string, find its first character that appears only once.

Input:

```
swiss
```

Output:

```
w
```

### **Approach**

1. Count each character using a LinkedHashMap.
2. LinkedHashMap preserves insertion order.
3. Find the first entry with frequency one.

```
import java.util.*;

public class Main {

    public static Character firstNonRepeating(String input) {

        Map<Character, Integer> frequency =
            new LinkedHashMap<>();

        for (char ch : input.toCharArray()) {

            frequency.merge(ch, 1, Integer::sum);
        }

        for (Map.Entry<Character, Integer> entry :
                frequency.entrySet()) {

            if (entry.getValue() == 1) {

                return entry.getKey();
            }
        }

        return null;
    }

    public static void main(String[] args) {

        String input = "swiss";

        System.out.println(firstNonRepeating(input));
    }
}
```

**Complexity:**

- Time: \(O(n)\), assuming ordinary HashMap operations.
- Space: \(O(k)\), where \(k\) is the number of distinct characters.

This example demonstrates why choosing LinkedHashMap instead of HashMap can matter: you need both efficient frequency counting and insertion order.

## **Assignment 2 — Performance optimization**

Given the following code:

```
import java.util.*;

public class Main {

    public static void main(String[] args) {

        List<Integer> numbers = new LinkedList<>();

        for (int i = 0; i < 100000; i++) {

            numbers.add(i);
        }

        long sum = 0;

        for (int i = 0; i < numbers.size(); i++) {

            sum += numbers.get(i);
        }

        System.out.println(sum);
    }
}
```

Identify the performance problem and optimize it.

**Solution:**

The code uses indexed access on a LinkedList.

Each indexed lookup requires traversal. Repeating this for every index can produce \(O(n^2)\) time.

Two improvements:

```
List<Integer> numbers = new ArrayList<>();
```

Or retain LinkedList but use sequential iteration:

```
for (int number : numbers) {

    sum += number;
}
```

Both avoid the repeated indexed traversal.
